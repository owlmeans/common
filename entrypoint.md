# OwlMeans: Module → Entrypoint Migration

> Design document for the rename of the OwlMeans "module" concept to "entrypoint" across the
> full ecosystem. This file is the single source of truth for the migration architecture and
> per-repo execution plan. **Do not edit this file during any `.md` update sweep.**

---

## Why

OwlMeans calls its core abstraction a **module**: a registered, addressable unit that is
simultaneously a server-side callable handler (HTTP or direct invocation) *and* a client/web/native
UI route. A context may hold dozens of them; they can be composed, nested, guarded, and called
across service boundaries.

The name collides severely with the JS/TS concept of "module" (an ES module file, a CommonJS
`require`, a TypeScript namespace). Coding agents — and human readers — regularly confuse the two
when reasoning about import paths vs. registered callable units. The confusion surfaces as:

- Agents suggesting `import { module } from '@owlmeans/module'` then treating `module()` as a
  file-level concept rather than a registered service unit.
- Docs and skills having to add `(not an ES module)` disclaimers constantly.
- Agent tooling guessing that `ctx.module(alias)` is related to the JS module system.

The replacement term is **entrypoint**: a single word, near-zero overlap with JS/TS vocabulary,
and naturally correct for both roles — "you enter the system here", whether you're navigating to a
UI route or calling a service handler.

## Locked Decisions

| # | Topic | Decision |
|---|---|---|
| 1 | **Package structure** | New canonical packages (`@owlmeans/entrypoint`, `@owlmeans/server-entrypoint`, `@owlmeans/client-entrypoint`). Old packages become deprecated reexport shims. |
| 2 | **Rename depth** | Full rename — every `Module*` symbol → `Entrypoint*`, including the `_module` marker property. |
| 3 | **Context method shape** | Mirror current shape 1:1 for clean deprecated aliases: `ctx.entrypoint(alias)`, `ctx.entrypoints()`, `ctx.registerEntrypoint()`, `ctx.registerEntrypoints()`, `ctx.hasEntrypoint()`. |
| 4 | **Deprecation lifecycle** | Keep all deprecated shims and aliases indefinitely. No removal phase in this plan. (Protects the `native` monorepo and any external consumers.) |

## Architecture

### New canonical packages

Three new packages are created under `packages/`:

```
packages/entrypoint/        ← replaces packages/module/
packages/server-entrypoint/ ← replaces packages/server-module/
packages/client-entrypoint/ ← replaces packages/client-module/
```

Each is a direct rename/copy of its predecessor with all `Module*` symbols renamed to `Entrypoint*`
per the naming map above. The `package.json` structure is identical (ESM + CJS dual exports, `.` +
`./utils` subpaths).

The new packages publish as `@owlmeans/entrypoint`, `@owlmeans/server-entrypoint`,
`@owlmeans/client-entrypoint` at the current monorepo version.

### Deprecated reexport shims

The old packages (`packages/module/`, `packages/server-module/`, `packages/client-module/`) are
converted to thin deprecated reexport shims. Their `package.json` names are unchanged; they gain a
dependency on their new canonical counterpart and their `src/index.ts` becomes:

```ts
// packages/module/src/index.ts (after shim conversion)

/** @deprecated use `entrypoint()` from @owlmeans/entrypoint */
export { entrypoint as module } from '@owlmeans/entrypoint'
/** @deprecated use CommonEntrypoint */
export type { CommonEntrypoint as CommonModule } from '@owlmeans/entrypoint'
/** @deprecated use CommonEntrypointOptions */
export type { CommonEntrypointOptions as CommonModuleOptions } from '@owlmeans/entrypoint'
// ... all other deprecated aliases ...
export * from '@owlmeans/entrypoint' // re-exports all new names too
```

This means any consumer still importing `@owlmeans/module` continues to compile and run — it just
sees `@deprecated` IDE warnings on the old symbol names. The `native` monorepo (out of scope) is
automatically protected.

### Context package (linchpin)

`packages/context/` is **not renamed** but is modified first, since everything depends on it.

Changes to `packages/context/src/types.ts`:
- Add `BasicEntrypoint` interface (`_entrypoint: true`) alongside `BasicModule`.
- Add new canonical methods to `BasicContext<C>`: `registerEntrypoint`, `registerEntrypoints`,
  `entrypoint(alias)`, `entrypoints()`, `hasEntrypoint`.
- Mark old methods (`registerModule`, `registerModules`, `module`, `modules`, `hasModule`) and the
  `BasicModule` interface as `@deprecated` delegating aliases.

Changes to `packages/context/src/context.ts`:
- Rename internal registry `allModules` → `allEntrypoints` (private, no compat concern).
- Implement the five new canonical methods; old methods delegate to them.

### Marker interop rule

During the deprecation window, code built against either the old or new package must be interoperable
in the same context. The factory in `packages/entrypoint/` sets **both markers**:

```ts
const ep = appendContextual<CommonEntrypoint>(route.route.alias, {
  _entrypoint: true,
  _module: true,     // kept for compat — code still checking _module: true still works
  ...
})
```

`isEntrypoint()` recognizes either marker:

```ts
export const isEntrypoint = (obj: object): obj is CommonEntrypoint =>
  '_entrypoint' in obj || '_module' in obj
```

`isModule()` in the deprecated shim delegates to `isEntrypoint`.

### GOTCHA — ESM bundler fields

`package.json` files contain a top-level `"module"` field and an `exports` `"module"` condition
(e.g. `packages/module/package.json` lines 12, 19, 27). These are bundler/tooling fields unrelated
to our concept. **A find/replace on the word "module" must never touch `package.json` field names.**
Only rename npm package *names* (the `"name"` field) in new packages; leave all field keys intact.

### Build and dependency order

Existing direction: `context` ← `module` (module depends on context, not vice-versa).

Execution order for Phase 1:
1. `packages/context/` — linchpin, must be first
2. `packages/entrypoint/` — new canonical core
3. `packages/server-entrypoint/` and `packages/client-entrypoint/` — parallel
4. Shim packages (`module`, `server-module`, `client-module`) — after their targets exist
5. All consumers (~31 packages) — after shims exist

Update `tree.md` to add the three new packages in the correct build order position. Tsconfig project
references in new packages should mirror their predecessors.

### Shim interop test

A file that `import { module } from '@owlmeans/module'` and registers an entrypoint onto a context
that already has `registerEntrypoint` — it must resolve without runtime error. The `_module: true`
marker on the shim-created object is accepted by the new context's `hasEntrypoint` (which calls
`isEntrypoint`, which accepts either marker).

### After each external repo phase (Phases 3–5)

Same pattern per repo:
- `bun run build` green
- `grep` for residual old imports (excluding any intentional shim uses)
- Repo's own test suite green
