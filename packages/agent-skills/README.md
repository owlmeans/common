# @owlmeans/agent-skills

CLI installer that lifts embedded agent skills out of installed `@owlmeans/*` packages
and places them into your project's skill store.

## Usage

After installing `@owlmeans/*` packages, run once:

```sh
npx @owlmeans/agent-skills@^0.1.18-rc.12
```

The installer walks the **whole project tree** and reads every nested
`<dir>/node_modules/@owlmeans` scope it finds — not just the one at the root. That is
what makes a bun workspace work: a scaffolded app keeps its `@owlmeans/*` dependencies
in its workspace packages, so the root often has no `@owlmeans` scope at all. The walk
never descends into a `node_modules` directory, skips hidden directories, and follows
each package only once however many places it is linked from.

Every `agent-meta/manifest.json` found that way is read, you are shown what guidance is
available, and (with your confirmation) it is copied into
`.agents/skills/<name>/SKILL.md` — the [Agent Skills](https://agentskills.io) standard
location, discovered natively by GitHub Copilot, Codex and other agents. When two
packages ship a skill of the same name, the highest version wins; `-rc` prereleases are
compared by semver precedence, so `0.1.18-rc.12` beats `0.1.18-rc.5`.

Claude Code reads skills only from `.claude/skills/`, so a project that already has a
`.claude/` directory also gets a per-skill symlink there. Repos generated by
`@owlmeans/create-app` keep those symlinks fresh with
`sh .agents/scripts/link-skills.sh`, run automatically at session start.

Re-run after updating `@owlmeans/*` packages to pick up revised guidance.

## Flags

```
--dir <path>        target project directory (default: current working directory)
--yes, -y           skip interactive confirmation (conflicts stay skipped, exit 0)
--only <pkg,...>    install guidance from these packages only (comma-separated @owlmeans/* names)
--extras            include extras bundled in the installer itself (default: on)
--no-extras         skip extras bundled in the installer
--force             overwrite locally-edited files (no AUTO-GENERATED banner)
--dry-run           print plan without writing any files
--claude-only       accepted, does nothing — one skill store serves every agent
--copilot-only      accepted, does nothing — one skill store serves every agent
--help, -h          show this help
```

`--claude-only` and `--copilot-only` are kept so a script that still passes one keeps
working; each prints a note saying it was ignored. `--help` lists the same set.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Success — including a `--dry-run`, an aborted confirmation, and a run whose only leftovers were conflicts you asked it to accept (`--yes` / `--force`). |
| `1` | Fatal error. |
| `2` | Argument parse failure — an unknown flag, or `--dir` / `--only` without a value. |
| `3` | No embedded `@owlmeans/*` guidance found anywhere in the tree. Install the packages first. |
| `4` | Linked monorepo — nothing was written. Pass `--force` to install anyway. |
| `5` | Conflicts left unresolved by a non-interactive run. Every clean skill **was** installed. |

## Conflict policy

Files managed by the installer carry an `AUTO-GENERATED` banner. On re-run:

- **Managed files** (banner present) — always updated to the latest embedded version.
- **Locally-edited files** (no banner) — **skipped** and reported as conflicts by default.
  Pass `--force` to overwrite, or confirm individually in interactive mode.

A conflict costs that one file and nothing else. The clean skills are installed on every
run, whatever the conflicts, and a skill left as a conflict still gets its
`.claude/skills/` symlink — the file is on disk and Claude Code has to see it.

What a non-interactive run (no TTY, or stdin redirected) does with the leftovers depends
on the flags:

| Flags | Behaviour |
|---|---|
| neither `--yes` nor `--force` | clean skills installed, conflicts listed, **exit 5** |
| `--yes` | clean skills installed, conflicts listed and accepted, exit 0 |
| `--force` | conflicts overwritten, exit 0 |

## Extras

Some guidance belongs to no single package: it describes how an agent should work in an
OwlMeans project at all — memory, self-education, git policy, skill authoring, scaffolding,
the shadcn design system. A skill becomes an extra by declaring

```yaml
metadata:
  scope: general
```

in its canonical frontmatter. Everything so marked is embedded into this installer's own
`agent-meta/`, alongside this package's own package skill, and is installed by default
even when no other `@owlmeans/*` package is present — which is how `@owlmeans/create-app`
gets harness guidance into a project before its first dependency install. Pass
`--no-extras` to install only what the project's own packages ship.

## Linked monorepo

If any `@owlmeans/*` packages are **symlinked** (e.g. via a `libraries/` workspace
link in an OwlMeans monorepo), the installer refuses and exits with code 4. There the
canonical skills already sit in the linked monorepo's root `AGENTS.md` and
`.agents/skills/`, and `sh .agents/scripts/link-skills.sh` — run by the committed
`SessionStart` hook — is what puts them in front of each agent. Installing embedded
copies on top would only add stale duplicates.

Pass `--force` only if you understand this and want to proceed anyway.

## Schema

Each `@owlmeans/*` package ships its embedded guidance under:

```
agent-meta/
  manifest.json          # package, version, entries list (schemaVersion 2)
  skills/<name>/
    SKILL.md             # agent skill
```

Packages published before schema v2 also carry `instructions/<name>.instructions.md`,
the GitHub Copilot twin of the same knowledge. Those entries are ignored on install.

Embedded files are **generated and read-only**. To contribute guidance edits, open
a PR against [owlmeans/common](https://github.com/owlmeans/common).

## Package skills in a prompt (`@owlmeans/agent-skills/llm`)

`owlmeansPackagesPlugin(options)` notices which `@owlmeans/*` packages a request mentions
and loads their published skills into the `Packages` block. Within a package there is no
relevance ranking — a package that was named gets everything it documents. Two ceilings
bound that anyway:

- `categories` — manifest categories to include, defaulting to `package-specific` and
  `multi-package`. `general` entries describe how an agent should behave rather than what
  a package does, so they belong in the host's own skill catalogue; ask for them
  explicitly if you want them here.
- `maxPackages` — how many mentioned packages load into one prompt, default `5`. A prompt
  that name-drops a dozen packages is rarely asking about all of them, and each one costs
  context.

Resolution order per package: the host's `LlmFileProvider` (the only path that sees a
sandbox or remote workspace) → an installed copy under `node_modules` → the canonical
repository over HTTPS. Every failure is a miss, never a throw. Results, including misses,
are cached per plugin instance.

```typescript
ctx.prompts().use(owlmeansPackagesPlugin({
  files: () => ctx.files(),      // tried first
  exclude: ['@owlmeans/llm'],    // already covered by the static Skills block
  fetch: false,                  // air-gapped: skip the repository fallback
  maxPackages: 5,                // default
  categories: ['package-specific', 'multi-package'], // default
}))
```

The manifest deliberately carries no git ref — version-matching comes from shipping the
copy inside the tarball, so for a package that is NOT installed the ref is a plugin option
(`ref`, default `main`).

## Project skills in a prompt (`@owlmeans/agent-skills/llm`)

`projectSkillsPlugin(options)` loads the skills the **project itself** has installed — the
[Agent Skills](https://agentskills.io) standard's `.agents/skills/<name>/SKILL.md`
directories, read through the host's `LlmFileProvider` and never through `node:fs`, so it
works against a sandboxed or remote workspace.

A skill's two halves land in two blocks, because they have different cache lifetimes:

| Half | Block | Changes | Content |
|---|---|---|---|
| index | `Skills` | per project | `- <name> — <description>`, sorted, capped, clipped |
| body | `Packages` | per request | the full text of each activated skill |

That is progressive disclosure expressed as a cache layout: the model always knows what
exists, and pays for a skill's text only when something says the call is about it.

```typescript
ctx.prompts().use(projectSkillsPlugin({
  files: () => ctx.files(),
  rules: [
    { skills: ['deploy'], when: { paths: ['charts/**', '*.yaml'] } },
    { skills: ['auth-protocol'], when: { purposeType: ['coder'], mention: ['token', 'guard'] } },
  ],
}))
```

Activation, in precedence order and capped by `maxActivated` (3): names the call itself asked
for → the deterministic `rules` → the host's `activate(signals)` → optionally one cheap
`utility()` model pick (`relevanceModel: true`, off by default, memoised so a retry re-sends
identical bytes). Bodies are claimed via `ctx.claim('skill:<name>')`, and
`owlmeansPackagesPlugin` claims first: a request that names `@owlmeans/auth` is a more
specific signal than a rule.

| Option | Default | Meaning |
|---|---|---|
| `dir` | `.agents/skills` | Where the skills live, relative to the project root. |
| `files` | — | Fallback provider; the compose context's own wins. |
| `rules` | `[]` | Deterministic activation rules. |
| `activate` | — | The host's own activation decision. |
| `exclude` | `[]` | Names neither indexed nor activated. |
| `maxActivated` | `3` | Bodies loaded into one prompt. |
| `maxIndexEntries` | `40` | Index lines. |
| `descriptionChars` | `160` | Description length in an index line. |
| `maxBodyChars` | `24000` | Length one activated body is clipped to. |
| `relevanceModel` | `false` | Spend one cheap-model call on the pick. |
| `listTtlMs` | `30000` | How long a directory listing is trusted. |

A file whose frontmatter is invalid — no `name`/`description`, a name outside
`[a-z0-9-]{1,64}`, or a name that differs from its directory — is skipped silently. Parse one
yourself with `parseSkillFile(path, content)`.

Inside an agent run, `projectSkillsAgentPlugin({ files })` adds a `read_skill(name)` tool for
the turn that needs a body composition could not have predicted:

```typescript
makeAgentModel({ exec, tools, plugins: [projectSkillsAgentPlugin({ files: () => ctx.files() })] })
```

After writing a skill file into a project an agent is still working in, call
`invalidateProjectSkills(providerKey)` so the next prompt sees it.
